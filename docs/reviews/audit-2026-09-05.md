## Overall assessment

**NYC Transit Live is a substantial, thoughtfully engineered transit visualization application with a strong testing foundation. Its next development phase should focus on the accuracy and consistency of the information riders see, continuous recovery, and everyday usefulness.** Several remaining defects allow old, canceled, incomplete, or historically obsolete information to look more reliable than it is. Those defects deserve attention before another major expansion in transit coverage.

The architecture is appropriate for the current product: one FastAPI process polls upstream providers, normalizes their data, serves cached JSON, and delivers a Leaflet frontend without a production JavaScript build chain. This avoids multiplying upstream requests by the number of visitors. The implementation goes well beyond a basic map: it handles partial outages, previous-stop inference, route-following animation, unstable PATH identities, service alerts, source-specific empty-feed behavior, mobile focus management, and many accessibility details.

The strongest criticism is about **semantic correctness**. Passing a protobuf decoder, matching a golden fixture, completing an HTTP request, and producing a green operational status do not necessarily mean that the resulting passenger information is current or correct. The audit found examples of each distinction.

| Area | Assessment |
| --- | --- |
| Architecture | Well suited to a small deployment; growing coupling and single-process assumptions need deliberate management. |
| Transit correctness | Sophisticated joins and inference, with consequential remaining gaps in cancellation, observation age, and historical reference data. |
| Resilience | Strong handling of many realtime failures; incomplete recovery after partial static startup failures and no continuing static refresh. |
| Security | Useful defensive controls and a limited public, read-only surface; no critical exploitable vulnerability demonstrated in this review. |
| Tests and delivery | Strong automated foundation, all locally completed suites passed; domain invariants must challenge the golden expectations. |
| Accessibility | Considerable measured work and unusually candid documentation; important functional gaps remain. |
| Performance and scale | Reasonable current design, but no demonstrated fleet-scale browser or production load budget was available. |
| Product opportunity | Strong foundation for dependable station/departure boards, saved commute views, and disruption information. |

This is a codebase assessment, not a certification of uptime, security, accessibility conformance, or all live transit data. Findings below identify their evidence and limits.

## Existing architecture and strengths

| Surface | Existing behavior | Main boundary to preserve |
| --- | --- | --- |
| Subway | GTFS-RT predictions, station placement, route geometry, inferred movement, station arrivals and alerts | Estimated positions must remain distinguishable from actual observations. |
| Buses | Reported positions and headings, route drawing and route alerts | Credential handling, observation quality, and an equivalent text interface. |
| LIRR / Metro-North | GPS where available, TripUpdate-derived placement otherwise, arrivals and route geometry | Providers have different identifiers and timestamp behavior; one freshness rule cannot safely cover both. |
| PATH | Community bridge data, synthetic cross-poll identity, station arrivals and route-following animation | Bridge availability and generation time do not prove every underlying prediction is current. |
| NYC Ferry | Boat GPS, dock arrivals and alerts; successful empty feeds clear boats | VehiclePositions and TripUpdates are separate information sources. |

| AirTrain JFK | Committed station, route and headway reference | Historical data must not appear to be a verified current timetable. |

Important strengths to retain:

- **One polling layer serves many clients.** In-memory snapshots and reusable HTTP clients keep upstream traffic independent of browser count within the documented single-worker deployment.
- **Failure isolation is deliberate.** Per-system retention, bounded refreshes, malformed-feed rejection, controlled empty-feed semantics, and synthetic outage tests handle failure classes that many transit projects omit.
- **The source adapters reflect actual provider differences.** PATH identity matching, railroad placement fallbacks, NJT cancellation/dwell handling, and system-qualified station IDs show meaningful domain work.
- **Static publication is staged.** Temporary files, validation and atomic promotion protect existing caches for many failures. F08 and F09 identify holes in that protection, not an absence of the mechanism.
- **The frontend takes accessibility seriously.** Native station controls, a skip link, reduced-motion support, focus restoration, mobile inertness, restrained announcements, and tests that challenge the accessibility scanner's coverage are valuable.
- **Security controls fit the application.** Same-origin scripts and self-hosted Leaflet reduce script supply-chain exposure at runtime; credentialed NJT requests reject redirects; error sanitization protects upstream secrets; bus route identifiers are constrained before filesystem lookup. A public read-only transit API does not need authentication merely to satisfy a generic checklist.
- **Tests are layered.** Fast unit tests, captured-feed fixtures, browser checks and a real-backend contract tier provide complementary evidence. Preserve that division.

### F01 — Old LIRR GPS observations can look live

**Evidence:** [railroad GPS decoder, lines 54–124](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/feeds/railroad.py#L54), [railroad model](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/models.py#L39), and the committed [LIRR protobuf capture](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/tests/fixtures/railroad_lirr.pb).

The GPS decoder accepts a positioned vehicle inside the geographic bounds, discards its individual `vehicle.timestamp`, and leaves `now` unused. The frontend then receives a position accompanied by feed-level freshness, with no observation age.

The capture contains 69 positioned LIRR vehicles. Relative to **that capture's own feed header**, 42 observations are over 90 seconds old, 32 over five minutes, and 25 over ten minutes. The oldest is **14 hours, 54 minutes, 36 seconds** old. Running the complete railroad aggregation against the committed LIRR/MNR captures still emits all 69 LIRR GPS records, with no failed systems. These ages are measured within the captured feed; they are not calculated by comparing the fixture's historical date to today's date.

**Impact:** the map can imply that a train is currently at a location recorded many hours earlier.

**Remedy:** carry `observed_at` and position provenance, validate age using a provider-specific policy, and use fresh TripUpdates as a fallback where possible. Filtering the GPS output alone will not restore estimated positions: the [placement pass](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/feeds/railroad.py#L290) independently classifies every positioned entity as GPS-equipped and suppresses its schedule placement. Both passes need the same set of accepted GPS identities. Preserve Metro-North's distinct timestamp policy rather than applying a LIRR cutoff indiscriminately.

**Acceptance:** a fresh header containing an old vehicle observation never produces an unqualified live-GPS marker; a usable prediction can produce a clearly labeled estimated marker instead.

### F02 — Canceled services remain normal GPS markers

**Evidence:** [GPS emission](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/feeds/railroad.py#L83), [cancellation filtering only in the placement/arrivals pass](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/feeds/railroad.py#L305), and [the golden expected output](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/tests/fixtures/railroad_lirr_expected.json#L7).

The captured LIRR TripUpdate `6004XX_2026-06-20_T` marks its trip `CANCELED`, while a separate GPS entity remains present. The application emits that trip as route 5, train 508. The canceled train is the first record in the expected golden output. Synthetic checks also reproduce the issue in the combined TripUpdate/VehiclePosition layout used by Metro-North.

The existing cancellation filter correctly removes predictions and station placement, but runs after GPS records have already been accepted. Thus the station board and map can disagree about whether this is a passenger service.

**Remedy:** resolve cancellation/deletion before GPS emission, checking both vehicle descriptors and associated TripUpdates. Suppress canceled passenger-service markers or explicitly present them as canceled/nonservice observations if that becomes a deliberate product feature. Handle `DELETED` consistently with the [GTFS-Realtime specification](https://gtfs.org/documentation/realtime/reference/). Correct the golden expectation and add an independent invariant so the fixture cannot bless this behavior again.

**Acceptance:** the captured canceled LIRR trip does not appear as a normal active service; test both separate and combined entity layouts.

### F03 — Station countdowns lose upstream content freshness

**Evidence:** [subway arrivals response](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/routes/subway.py#L85), [arrival models](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/models.py#L191), and [popup age calculation](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/frontend/helpers.js#L713).

A valid subway feed with a header ten minutes old and a prediction two minutes ahead was passed through the real decoder, refresh path and endpoint. The vehicle response exposed approximately 600 seconds of content lag. The station-arrivals response instead exposed a newly stamped `fetched_at`, the prediction, and no content-age field. The popup and station panel derive freshness from that acquisition timestamp.

The existing per-contributing-group logic correctly handles failed fetches. It does not handle repeatedly successful retrieval of old information. Similar arrivals envelopes for other modes also omit content freshness, so the shared design needs correction even though the end-to-end reproduction here used subway data.

**Remedy:** give arrivals their own source/content time, served time and freshness state. Mixed subway boards need contributor-aware freshness, and ferry arrivals should use the TripUpdates clock rather than the independent boat-position clock. Reuse the same freshness interpretation across map, popup, station panel and departure boards.

**Acceptance:** repeatedly returning an old, valid HTTP-200 feed makes its countdowns visibly qualified as stale; other healthy contributors remain distinguishable.

### F04 — AirTrain's historical fixture looks like current scheduled service

**Evidence:** [fixture provenance and Terminal 2](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/data/airtrain_jfk.json#L2), [provenance removed from the API](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/airtrain_static.py#L60), and [current-time headway rendering](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/frontend/stations.js#L529).

The committed fixture says its source calendar expired **December 31, 2021** and is not a live schedule authority. It still includes Terminal 2. The backend drops the provenance, while rider surfaces choose headway bands using the current New York time and describe them as scheduled service.

The Port Authority [announced that AirTrain's Terminal 2 station had closed for demolition in July 2022](https://www.panynj.gov/port-authority/en/press-room/press-release-archives/2022-press-releases/bridges--tunnels-and-rail-advisory-for-july-22-to-28.html). This demonstrates an actual obsolete station, beyond the age of the source alone. “No live tracking” does not communicate that the reference itself is historical.

**Remedy:** verify and replace the active station inventory and geometry using current official information; expose source and review dates. Withhold unverified present-day headways or visibly identify them as historical reference. Link the [official AirTrain page](https://www.jfkairport.com/transportation/airtrain) for current travel information. Tests should validate current supported service, not permanently enshrine the existing station count.

**Acceptance:** closed historical stations are absent from active service, and no expired timetable is presented as a verified current schedule.

### F05 — Failed NJT token mints can repeat rapidly

**Evidence:** [TokenCache.get](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/njt_auth.py#L661), [existing failed-mint test](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/tests/test_njt_auth.py#L389), and [documented account budget](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/README.md#L472).

The lock serializes callers and shares a successfully minted token. A failed mint leaves no shared failure/cooldown state. In a hermetic reproduction, **12 concurrent callers invoked the failing mint callback 12 times** and obtained zero tokens. Subsequent position polls, alert polls and warmup attempts can try again.

The README records an observed ten-attempt daily account limit, with failed attempts counted, and describes a shared monitor/production budget. That provider charging behavior was not independently retested in this audit. **If the recorded behavior remains correct, a short authentication failure can consume the remaining daily budget and disable NJT until reset.** Repeated failed requests are proven; the account-wide quota consequence is conditional on that recorded upstream behavior.

**Remedy:** share in-flight failures as well as successes; add bounded exponential backoff and a circuit breaker; distinguish a transient network failure, invalid credentials, rejected token and exhausted daily quota. Expose a safe retry-after state. Before replication, coordinate or persist the relevant token/budget state. Correct the README's claim that failed mints are never retried anywhere.

**Acceptance:** a burst of concurrent callers during a failed mint produces one attempt for the failure-sharing window, subsequent calls respect cooldown, and a known quota refusal does not cause continued rapid mint requests.

### F06 — Partial static startup failures persist until restart

**Evidence:** [railroad warmup](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/warmups.py#L192), [bus index task](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/bus_static.py#L301), and [startup scheduling](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/main.py#L323).

Railroad warmup retries when both systems fail. If one succeeds, it marks the aggregate `ready` and terminates. Injecting a first-call-only Metro-North failure left `MNR_stops=None`, aggregate status `ready`, and exactly one attempt per system, even after the shortened retry interval elapsed. Bus indexing likewise terminated after one injected failure although the second call was programmed to succeed. Partial bus builds also rely on a later startup for another build.

**Impact:** a temporary startup failure can leave missing railroad stations, arrivals and geometry, or missing bus route geometry, for the entire process lifetime. Working GPS markers can make the partial railroad loss less obvious.

**Remedy:** keep successful components available while independently retrying failed operators/boroughs. Publish per-component readiness and degradation. Coordinate frontend static-data reloading: a loader that stops permanently after the first partial nonempty response will otherwise miss repaired data.

**Acceptance:** one provider fails at boot, recovers without a deployment, and its stations/routes appear in an already-open browser without a manual reload.

### F07 — Static schedules do not refresh after successful warmup

**Evidence:** [startup-only tasks](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/main.py#L323), [successful warmup returns](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/warmups.py#L184), and [NJT load-time age/validity checks](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/njt_static.py#L968).

Cache-age and service-calendar checks run when loaders execute. Successful warmup tasks return permanently. A long-lived process can cross an archive-age threshold or a schedule's validity boundary without reloading, revalidating or attempting a new publication.

**Impact:** route geometry, trip joins, station service and NJT schedules can remain outdated despite healthy realtime HTTP traffic. Frequent deployments may incidentally conceal the problem; they are not a refresh policy.

**Remedy:** periodically construct and atomically publish complete immutable snapshots, retaining the last usable one during failures. Use publication changes and service validity to select refresh times. Report snapshot version, loaded time, valid-through date and next refresh. Let clients detect changed static versions and update their registries safely.

**Acceptance:** simulate a validity boundary and a changed publication in a running service; the new snapshot is adopted without restarting, while a bad replacement leaves the prior usable snapshot intact.

### F08 — Bad subway geometry can replace known-good geometry

**Evidence:** [subway publication validator](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/static_data.py#L61) and [route loader](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/static_data.py#L251).

Validation requires `shapes.txt` to exist but does not parse it. Starting from an archive yielding one route, a replacement with invalid UTF-8 only in `shapes.txt` passed the actual staged-publication validator and overwrote the good archive. Route count then fell to zero. Archive status reported successful promotion, no download error and zero failed downloads.

**Remedy:** validate required usable geometry before promotion, including the derived route output that will be served. Test empty and unreadable geometry independently of stop validation. Preserve valid old geometry when a replacement fails.

**Acceptance:** both malformed and unusably empty required geometry are rejected before replacing the cache, and rejection appears in operational status.

### F09 — Invalid numeric coordinates can corrupt output or kill warmup

**Evidence:** [subway coordinate parser](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/static_data.py#L146), [NJT shape parser](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/njt_static.py#L316), [geometry rounding](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/route_geometry.py#L343), and [NJT derivation outside the guarded load](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/warmups.py#L405).

`float()` accepts values such as `nan` and `inf`. The parsers do not consistently apply finite and geographic range checks. An actual subway-stops ASGI response containing a parsed NaN returned **HTTP 200 with `lat:null`**, rather than a 500; the frontend passes that coordinate directly to Leaflet, where null is numerically coerced to zero.

A separate NJT reproduction passed accepted NaN shape points into the real geometry builder. It raised `ValueError: cannot convert float NaN to integer`. Because derived geometry is built outside the warmup's catch/retry block, the task terminated while its status remained `loading`.

**Remedy:** centralize finite/range validation, validate the complete derived snapshot, and keep all derivation inside the warmup failure boundary. Do not publish partial application state before successful construction.

**Acceptance:** malformed numeric rows cannot become null/zero map points or leave a completed failed task labeled as still loading. These are fault-injection results, not evidence of malformed coordinates in today's live provider feeds.

### F10 — Timeout failures disagree across health surfaces

**Evidence:** [deadline wrapper](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/pollers.py#L137), [wrapper composition](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/pollers.py#L1006), and [majority-outage classification](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/routes/status.py#L259).

The deadline wrapper catches its timeout, records a 504, and marks the response envelope's systems failed. It does not call the separate degradation callback. The outer wrapper receives a normal return, leaving the operational health map unchanged.

The exact composed path was reproduced with old subway data, an initially healthy eight-group subway health map, and a fresh bus feed. Afterwards, the subway cache recorded 504 and envelope systems had `ok:false`, but the operational map still said all eight groups were healthy and health classifications were empty.

**Remedy:** normalize timeout degradation through the same source-specific path used by other failures. Assert status, envelope and classification agreement together.

**Acceptance:** a subway refresh deadline is visible as subway degradation on every relevant surface. Keeping readiness HTTP 200 when another mode is usable can remain an explicit availability decision; the falsely empty degradation list is the defect.

### F11 — The station panel hides relevant service alerts

**Evidence:** [station-detail renderer](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/frontend/stations.js#L606), [map popup alert matching](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/frontend/systems/shared.js#L1319), and [mobile inert behavior](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/frontend/stations.js#L131).

The panel renders arrivals without consulting the alert store. Popups use station/route matching, but station-specific and route-specific alerts are excluded from the agency-wide banner. Executing the production renderer and helpers with a station-specific service suspension produced an alert in the popup helper, no banner entry, and ordinary arrival text in the panel.

On a phone the open panel makes the map inert, so the hidden popup is not an equivalent active source of information. This affects the application's primary text and keyboard interface.

**Remedy:** reuse the station/route alert matcher in the panel, including alert-source freshness. Announce meaningful alert changes without speaking every countdown tick.

**Acceptance:** station suspension appears in both surfaces, including when no trains of the affected route are currently predicted.

### F12 — An old station's delayed error can overwrite the current station

**Evidence:** [panel error-response path](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/frontend/stations.js#L464).

The controller checks its sequence after response headers arrive, then awaits error JSON without another sequence check. In the reproduced sequence, station A's 503 headers arrived; the user selected B; B's successful data rendered; then A's delayed error body completed and set the shared panel error. B remained selected but its good arrivals were hidden behind A's warming message.

**Remedy:** recheck request identity immediately after each awaited body read, including error branches. Audit analogous popup and bus-route error branches. A shared arrivals request controller would reduce this duplication.

**Acceptance:** split headers/body delivery in a regression; neither an old successful body nor an old error body may change the selected station's state.

### F13 — Railway healthchecks do not provide continuous recovery

**Evidence:** [healthcheck commentary](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/routes/status.py#L320), [deployment configuration](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/railway.json), and [six-hour monitor schedule](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/.github/workflows/contract-monitor.yml#L22).

Some comments justify health decisions by saying Railway restarts a container on a failed healthcheck. Current [Railway documentation](https://docs.railway.com/deployments/healthchecks) says its configured endpoint is checked during deployment, not continuously after going live. A running process with a dead task or stale data therefore does not receive automatic recovery solely because `/healthz` changes to 503. The repository-defined production monitor runs every six hours.

**Remedy:** add a lightweight frequent application monitor, alert routing, and background-task heartbeat/supervision. Check data-quality fields as well as HTTP reachability. Keep this separate from the credentialed upstream contract monitor so more frequent monitoring consumes no additional NJT mints. Restart local failed tasks when appropriate; avoid restarting the application merely because an upstream provider is unavailable.

**Acceptance:** a simulated stopped poller is detected promptly after startup and reported or recovered according to policy. External monitoring could already exist in platform settings; that was not inspectable here.

### F14 — Important accessibility functions remain unavailable

**Evidence:** [documented exceptions](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/ACCESSIBILITY.md), [bus popup actions](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/frontend/systems/buses.js#L270), and [issue #88](https://github.com/rosenfieldben/nyc-transit-live/issues/88).

The existing statement candidly acknowledges that updates cannot be paused, arbitrary pointer panning relies on dragging, buses have no station-panel equivalent, and no manual assistive-technology testing has been performed. These are known limitations, not newly discovered regressions. Removing individual markers from Tab order is sensible at fleet scale, but bus popup information, route alerts and route drawing then have no keyboard equivalent.

**Remedy:** add a searchable bus-route/vehicle text surface, a pause/resume control that freezes motion and countdowns together while showing data age, and single-pointer pan controls. Add critical-flow WebKit/Firefox checks and manual VoiceOver/NVDA sessions, including a disabled-rider review. Test zoom/text enlargement and focus visibility in combined overlays.

**Acceptance:** complete a bus information task by keyboard; freeze/resume the page honestly; pan to arbitrary areas without dragging. Preserve the existing accessibility statement's distinction between measured behavior and conformance.

## Engineering improvements beyond the findings

### Establish a common data-quality contract

The highest-value architectural change is a consistent contract carried from provider adapter to every rider surface:

| Field/concept | Purpose |
| --- | --- |
| `fetched_at` | When the application successfully acquired the information. |
| `content_at` | When the provider generated the relevant feed content, where meaningful. |
| `observed_at` | When an individual vehicle position or prediction was measured/updated, where available. |
| `served_at` | When this API response was generated. |
| Source and method | Provider, GPS versus inferred/estimated versus scheduled/historical reference. |
| Quality state and reason | Fresh, stale, unavailable, canceled, unknown, or historical; explain why. |
| Static snapshot identity/validity | Which station/route/trip tables informed a join, and whether their service period is valid. |

These are design concepts, not a demand to populate unknown timestamps with invented values. Unknown should remain explicit. PATH and Metro-North need provider-specific interpretations. An upstream HTTP-200 freeze cannot be detected by acquisition age alone if every poll keeps succeeding.

Use immutable snapshot construction and one publication step. Shared arrival stores should supply popup, station panel, future departure boards and notifications so those surfaces cannot silently diverge.

### Reduce coupling incrementally

The frontend has large shared files: `helpers.js` has 2,574 lines, `systems/shared.js` 1,579, and `stations.js` 813. Ordered scripts share global state. The backend also re-exports a broad patching surface through `main`, with pollers and warmups reading dependencies back through it to preserve existing tests. This works, but makes module boundaries less independent than their filenames suggest.

Migrate incrementally toward native ES modules and explicit controllers/stores. In Python, inject adapter and loader dependencies at the service boundary instead of extending the `main` monkeypatch contract indefinitely. Keep domain functions pure and keep the build/deploy simple. A wholesale frontend-framework or backend rewrite is not justified by this review.

Move lengthy historical review narratives into compact decision records, retaining short explanations of present invariants beside code. Repair stale README examples and phase notes: for example, the tree still names `feeds.py` although feeds are now a package, and some completed-phase prose describes behavior later phases replaced. Documentation should make today's behavior easy to find.

### Define performance budgets before optimizing

The normal page polls six live endpoints every 15 seconds and alerts every 60 seconds, even when layer toggles hide their visuals. Ignoring startup/static calls and optional station/popup requests, this is approximately **25 API requests per active client per minute**. At 1,000 concurrently active clients, the same pattern is approximately **417 requests per second**. This is arithmetic from the polling code, not a measured server capacity or traffic forecast.

Upstream polling remains shared in one worker, but response validation/serialization/compression and outbound bytes still scale with client traffic. Train animation updates visible layers at roughly 10 Hz, including trains outside the viewport. There is no application-level page-visibility lifecycle policy. Browser background throttling may reduce actual work; it is not an explicit application contract.

Measure representative full fleets on a slower phone and measure API throughput with realistic compressed payloads. Track p95 response latency, payload bytes, process memory, event-loop lag, long tasks and interactive frame rate. Then consider viewport culling, avoiding unchanged marker writes, hidden-tab suspension with immediate refetch on return, shared arrival requests, and snapshot-aware caching. A consolidated feed endpoint or server-sent events can reduce request overhead later, but should follow evidence rather than precede basic profiling.

The basemap uses public OpenStreetMap tiles. Before pursuing sustained larger traffic or offline map storage, account for the [OSM tile usage policy](https://operations.osmfoundation.org/policies/tiles/), including its service limitations and restrictions on bulk/offline downloading. Select a suitable tile arrangement as part of scaling; do not treat the public tile endpoint as unlimited infrastructure.

### Treat multiworker operation as a separate design change

The README explicitly requires one worker. That is consistent with in-memory caches, process-local token state and startup polling. Simply increasing Uvicorn workers or replicas multiplies upstream polling and token consumers and creates separate versions of application state.

A reproduced additional constraint is [same-stem temporary-file cleanup](https://github.com/rosenfieldben/nyc-transit-live/blob/625861759bc6975dfe79323caaccf97f9ead3879/backend/static_shared.py#L329): a second concurrent download deletes the first one's active `.part` file. The second promotes successfully and the first fails. The last good cache remained valid. This is a **scaling constraint**, not a default single-worker outage discovered in production.

Before adding workers, separate ingestion leadership from serving, use shared snapshots where warranted, coordinate credential/token usage, and use interprocess-safe archive publication and abandoned-file cleanup. Scale the current process vertically within measured limits while those requirements remain unmet.

### Improve security and CI hardening proportionately

No immediate credential-exposure path or critical exploit was demonstrated. Useful next hardening steps are explicit read-only permissions in the general CI workflow, immutable Action commit pins, production dependency hashes, bounded upstream response/archive expansion sizes, and validation of finite positive timing overrides. Consider a `frame-ancestors` policy and verify transport headers at the deployed edge. These are hardening recommendations, not claims that their absence is presently exploitable.

The standard browser config combines zero retries with `trace: "on-first-retry"`; that trace mode produces no retry trace in this configuration. Use `retain-on-failure` if failure diagnostics are wanted, as the contract browser tier already does. Confirm branch protections and deployment gating in GitHub/Railway settings; the YAML alone cannot prove that failed CI blocks deployment.

The most valuable test additions are the acceptance cases attached to F01–F12, especially semantic invariants over real captures. A golden test should preserve known-correct interpretation, not every output the current implementation happens to produce. Avoid inflating test count with assertions that merely repeat the implementation.

## Product growth and development roadmap

The strongest direction is to make this a **dependable answer to “what should I take from here, and can I trust the information?”** The map is an effective entry point; repeat utility comes from getting a rider to their relevant station, departure or disruption quickly.

| Sequence | Work | User value | Completion measure |
| --- | --- | --- | --- |
| Release 1: information reliability | F01–F05, F10–F12; common freshness/provenance contract | Stops misleading positions, countdowns and hidden disruptions | All relevant regression scenarios pass; map and text views agree. |
| Release 2: continuous operation | F06–F09, F13; snapshot refresh and per-provider recovery | Temporary faults recover without a deployment | Cold-start partial failure heals; expired static data refreshes; stopped tasks are detected. |
| Release 3: everyday access | F14; favorite stations/routes, deep links, saved layer choices, alias/route-aware search | Faster repeat use and accessible bus information | A rider returns directly to the desired view; critical tasks work by keyboard and on mobile. |
| Release 4: departure boards and disruptions | Terminal boards, planned-work view, fuller alert detail and accessible-station equipment information | Makes the product useful before and during a journey | Relevant departures and warnings are visible together, each with source age. |
| Growth stage: measured scale and broader planning | Performance budgets, ingestion/serving separation if needed, transfer-aware planning, opt-in notifications | Supports a larger audience and more complex journeys | Capacity and data-quality targets are measured; new modes meet the same acceptance contract. |

This sequence describes dependencies and outcomes rather than promising dates without knowing development capacity. Small fixes such as F12 can ship quickly, while the shared freshness and static-refresh work should be designed as coherent changes.

The most promising feature opportunities are:

1. **Favorite stations and commute views.** Save a few station/route combinations locally first. Offer stable, shareable links containing the selected station, map position and layers. This creates repeat usefulness without immediately introducing accounts.
2. **Terminal departure boards.** Build Penn/Moynihan, Grand Central, Jamaica, Atlantic Terminal, Hoboken and Newark Penn views using the existing arrival model. Cross-provider station complexes require an explicit curated relationship; proximity and numeric ID collisions are not reliable joins.
3. **A complete bus text interface.** Search a route, see route alerts, select a vehicle or stop, and draw the route through native controls. Adding bus arrivals will require a suitable stop/prediction source and its own freshness contract; existing bus positions alone do not supply that feature.
4. **Disruption-first station pages.** Show the relevant alerts, useful details and planned work next to departures. The backend already distinguishes held-back future alerts; exposing planned work needs an explicit future-period view rather than mixing it into active incidents.
5. **Accessible-journey information.** Combine static station accessibility with current equipment outages and the affected platform/entrance relationships. The MTA documents [equipment and current-outage feeds](https://www.mta.info/developers/display-elevators-NYCT). “Wheelchair accessible” and “a usable accessible path exists right now” are different claims and require different evidence.
6. **Nearby stations and stops.** Offer optional geolocation with a manual alternative. The current Permissions-Policy disables geolocation, so this requires a deliberate policy and UI change. Do not collect location history merely to implement nearby search.
7. **Installable/mobile departure-board experience.** Cache the application shell and suitable static reference data while clearly labeling offline live information as unavailable or last known. Avoid presenting an old countdown as live and avoid unauthorized bulk caching of basemap tiles.
8. **Transfer-aware planning and notifications.** Add these after freshness and service validity are dependable. Transfer guidance needs walking times, service calendars, accessibility and disruption handling, not just a straight line between coordinates. Notifications should be user-selected and deduplicated; upstream outages should not manufacture service-change alerts.
9. **Historical reliability analytics or embeddable boards.** These could support transit enthusiasts, buildings, workplaces or public displays. Historical storage requires a purpose-built sampling/retention model; existing in-memory caches do not support retrospective performance claims. Treat commercial potential as a hypothesis to validate with users, not an established market conclusion.

More transit modes should be admitted through a clear readiness checklist: authoritative or explicitly labeled community source, stable identity strategy, timestamp semantics, cancellation handling, static service validity, outage/recovery behavior, text accessibility, source terms, and representative fixtures. That checklist protects the tool's credibility as coverage grows.

## Recommended next implementation package

Start with a small group of reviewable changes: railroad cancellation/observation validity; shared arrivals freshness; AirTrain reference correction; panel alert/error-state parity; and NJT failed-mint backoff. Each has a concrete witness in this audit and a narrow acceptance condition. Follow with continuous static recovery and refresh, using immutable snapshot publication so the stronger validation does not reduce availability.

The repository's engineering investment is real, and it gives these fixes a strong foundation. The key development goal is to ensure that its most polished surfaces also give the most accurate account of what is known, what is inferred, and what has stopped updating.

## Architecture and strengths

A FastAPI service owns upstream polling and serves cached JSON to a buildless Leaflet frontend. Static GTFS establishes stops, routes and geometry; real-time feeds provide observations or predictions. The frontend maintains stable markers and estimates some train movements along geometry. The documented deployment has one serving worker and process-local state. This is a sensible small-deployment design, but ingestion ownership must change before adding replicas.

| Mode | Implemented capability | Important boundary |
| --- | --- | --- |
| Subway | Route shapes, station complexes, estimated train placement and movement, arrival boards, alerts, route focus | Animated placement is an estimate from predictions, not continuous underground GPS. |
| MTA buses | GPS vehicles, route geometry and route alerts | No equivalent searchable bus-stop departure-board workflow in the current station panel. |
| LIRR and Metro-North | GPS and estimated placement, route geometry, train/station popups, departures and alerts | Metro-North direction and some timing information require explicit inference or unknown states. |
| PATH | Routes, stations, arrival boards and estimated train movement with synthetic stable identities | Relies on a community real-time bridge; ambiguous identity matches must remain conservative. |
| NYC Ferry | GPS boats, docks, departure boards, route geometry and service alerts | Static trip-to-route joins must remain current; successful overnight emptiness is distinct from failure. |
| NJ Transit rail | Routes, stations, trains, departures and alerts | Already implemented, despite outdated portions of the README; authentication quota is a shared operational constraint. |
| AirTrain JFK | Static stations, guideway and headway reference | Reference fixture is historical and needs correction before its timetable-like information can be trusted. |

Preserve the existing strengths: per-source failure isolation; explicit poll/content/serve timestamps; row provenance; retained-data labels; real-time versus estimated-position distinctions; stable marker identities; shared API caches; separate alert polling; contract tests against a simulated upstream; golden captured feeds; self-hosted Leaflet/fonts; a strict script content-security policy; environment-based credentials; pinned runtime dependencies; Dependabot; keyboard navigation, focus management and reduced-motion support. These are valuable foundations and do not justify a wholesale framework rewrite.

## Prioritized findings

### A01 High Repeated NJ Transit token rejection bypasses the cooldown

**Failure.** `njt_post` replaces an invalid token once per call, but a successful mint clears the cache's failure cooldown even if the data endpoint rejects that new token. Repeating this across normal polling cycles mints another token each time. The existing fix for failed mint requests does not cover successful minting followed by authentication rejection.

**Evidence.** Ten calls sharing one token cache, using a fake transport that always mints successfully and always returns the recognized invalid-token data response, produced **11 mint requests and 20 data requests**. Cooldown remained unset. Under the repository's documented ten-token daily account limit, quota enforcement would stop later mints only after the budget had already been consumed. The monitor and production also share account spending.

**Repair.** Enter a shared authentication-rejection circuit breaker when a newly minted token is rejected; invalidate that token and clear the breaker only after successful authenticated access or a deliberate bounded recovery probe. Preserve single-flight minting and the one-replacement path for ordinary expiry. Test repeated polling and concurrent static/feed/alert consumers, not only a single request.

### A02 High Subway archive validation can replace good data with a persistent failure

**Failure.** The staged subway validator verifies some members and the presence of required tables, but does not fully parse every table required for successful publication. A structurally complete archive containing unreadable `trips.txt` can replace the good archive. The warmup then fails while building the station-route index. Subsequent attempts accept the same newly cached archive as fresh and do not download a repair.

**Evidence.** A local staged-download reproduction promoted an archive with valid basic tables and invalid UTF-8 in `trips.txt`. Three attempts all raised `UnicodeDecodeError`; only one download occurred. Archive status reported a successful promotion and zero failed downloads. This is a stronger failure mode than the prior audit's geometry-only corruption finding.

**Repair.** Validate the complete required publication before replacement and retain the last fully usable snapshot. A parse failure in a supposedly valid cached archive must invalidate that cache or force a staged repair. Test good cache → bad publication → healthy publication, checking both continuity and eventual recovery.

**Related medium-priority NJT variant.** An optional `shapes.txt` member with damaged DEFLATE data passes NJT publication validation, then raises an uncaught `zlib.error` during parsing. Three local attempts failed with zero repair downloads. Honor the promised optional-geometry degradation for decompression errors, or reject the publication coherently before promotion.

### A03 Medium Empty arrival boards can hide a failed or stale feed

**Failure.** Subway station health includes only feeds that still have arrivals indexed at that station. When a failed feed's last retained prediction expires, its station key disappears and the endpoint falls back to the healthy aggregate poll time with `systems: null`. Separately, frontend board freshness uses poll time without preserving availability and provider-content age. Fixing only the backend therefore leaves stale-content and never-decoded empty-board cases.

**Evidence.** With failed ACE and healthy G, expiring A01's final arrival produced empty directions, a current aggregate `fetched_at`, and no contributor health, despite ACE remaining failed. Production frontend helpers also returned no warning for an empty board whose content was old but recently fetched, and for a never-decoded failed contributor. Both panel and popup can consequently say “No trains” without explaining unavailable data.

**Repair.** Maintain station-to-feed coverage independently of displayed predictions; preserve expected failed contributors after expiry or retention limits. Carry availability, unknown clocks and source-content age through the board renderer. Regression cases must distinguish genuinely fresh empty service from stale, failed and unknown empty service in both surfaces.

### A04 Medium Clock correction can leave countdowns and freshness permanently wrong

**Failure.** Browser/server skew is the minimum offset observed across the entire session. A later forward change to the device clock cannot increase that stored minimum. Corrected application time then runs ahead until reload, affecting departure countdowns, freshness labels and estimated motion.

**Evidence.** Calibrating a device five minutes slow and then supplying a fresh response after the device clock is corrected makes a zero-age source appear 300 seconds old. This was reproduced through production helpers.

**Repair.** Anchor a recent server timestamp to monotonic elapsed time, or detect wall-clock discontinuities and reset a bounded calibration window. Test forward and backward clock changes after initial skew; assert arrival countdowns, source age and train placement together.

### A06 Medium Static schedules never refresh after successful startup

**Failure.** Static warmups return when ready and are started once. File-age policies are checked during loading, not periodically in a long-running process. New schedules, trip IDs, routes and service-calendar expiry can therefore outlive the data loaded into memory. Frontend static loaders also stop after their first usable result.

**Impact.** New ferry trip IDs can lose route joins, schedule-dependent NJT behavior can retain an old service calendar, and route/station changes require a restart or reload. MTA states that railroad GTFS changes frequently and offers supplemented subway schedules updated hourly, so a startup-only strategy is materially different from current service coverage. This is another documented unresolved design limitation.

**Repair.** Add jittered, per-source refresh with staged validation, generation/version identifiers and atomic snapshot swaps. Keep last-known-good data on failure and ensure browsers discover changed static generations. Coordinate NJT refresh with the authentication budget. Test a process crossing a service-day boundary and a changing upstream publication without a restart.

### A09 Medium Upstream resource use is not sufficiently bounded

**Risk.** Static transfers have no byte ceiling, archive validation lacks member-count/uncompressed-size limits, and some parsing runs synchronously on the serving event loop. NJT's transport buffers the whole response. Timeouts do not preempt synchronous CPU work, so an oversized or pathological agency publication can impair all layers sharing the process.

**Evidence and boundary.** A harmless local validator taking 80 ms completed and promoted a stage inside an `asyncio.timeout(10 ms)` block after approximately 81 ms, without a timeout. This demonstrates a resource-control gap; it does not demonstrate a public-user exploit or malicious provider.

**Repair.** Set source-specific compressed and expanded byte limits, archive member/row ceilings and finite-coordinate validation before publication. Move expensive work off the serving loop; use a killable subprocess where a hard CPU deadline is required. Test oversized downloads and members, malformed numeric values, last-good preservation and health responsiveness during validation.

## Engineering and operations

### Architecture and maintainability

The current separation into feed adapters, routes, warmups and caches is useful. Its main scaling pressure is implicit coupling: test compatibility routes dependencies back through `main`, while frontend files share ordered-script global state. `helpers.js` is 6,079 lines and `systems/shared.js` is 3,347. Historical narrative and implementation coexist extensively.

Refactor incrementally into explicit domains: feed-generation results; source coverage and freshness; station-board shaping; geometry/interpolation; marker presentation; selection and view state; and API transport. Use typed success/failure/unknown-clock results so omitted, null and retained do not accidentally mean the same thing. Extract frontend ES modules with explicit imports; a large bundler or framework migration is optional. Move lengthy historical review narratives to linked decision records while retaining concise explanations of genuine invariants next to code.

Refresh the README from the implementation: its opening scope, file tree, NJT milestone list and accessibility-system list lag the current code. Maintain one capability matrix showing system, live/GPS/estimated/reference status, sources, limitations and last verification. Keep old build-phase histories separate from the onboarding guide. Normalize real filesystem paths in the Node loader-hook test so macOS development remains reliable.

### Security and dependencies

The application already has meaningful safeguards: same-origin script CSP, vendored frontend libraries, explicit refusal of credential-bearing NJT redirects, token-safe error handling, environment-based secrets and staged static publications. The runtime lock is shared by deployment and CI, and Dependabot covers Python, Actions and npm. No confirmed vulnerable dependency is reported here; a limited advisory review is not a full dependency clearance.

Add a pinned-dependency advisory scan and secret scan to CI. Declare an explicit `contents: read` permissions baseline for the main CI workflow; its effective repository defaults were not inspected. Pin Actions to reviewed commit SHAs with automated update support. Consider lock hashes and a generated software bill of materials. Preserve strict output escaping for provider-supplied strings and the existing restriction on authenticated redirect handling.

### Availability and scaling

The six-hour upstream contract monitor is valuable for drift detection but is too coarse to be the only availability signal. Add inexpensive production availability/latency checks and feed-age alerts at a cadence appropriate to the desired recovery time. They should read existing status and metrics rather than mint new NJT credentials. A green scheduled job should separately report which credentialed providers were actually checked and which were skipped.

Instrument poll latency, decode failures, source age, retained age, static generation age, join misses, partial source coverage, token spending/cooldown, event-loop lag, memory and API latency. Define liveness separately from readiness and degraded optional providers; do not create a restart storm merely because an agency is down. Add runbooks for bad static publication, quota exhaustion, frozen pollers and cold-start failure.

Keep one worker until ingestion leadership, shared snapshots and credential coordination are implemented. Adding workers now duplicates upstream polling and token spending, creates divergent in-memory identities and can race shared staging files. When measured demand warrants scaling, separate one controlled ingestion service from stateless API delivery backed by shared latest snapshots. Benchmark ordinary polling against alternatives before adopting SSE or WebSockets.

### Test strategy

The next tests should cross boundaries rather than add more examples of isolated helpers: repeated authentication rejection across poll cycles; bad static publication followed by a healthy one; partial failure followed by recovery; empty predictions after contributor expiry; unknown timestamp after a timestamped generation; browser-clock correction; and static-generation rollover in an already-open browser.

Keep Chromium coverage and add targeted Firefox/WebKit tests for focus, inert state, layout and selection. Add manual assistive-technology checks. Measure representative all-mode datasets on a constrained mobile device before claiming a rendering problem or changing mapping technology. Useful performance targets should be set after baseline measurements: time to first usable board, interaction latency, frame budget, memory growth and bytes transferred per active and hidden tab.

Its distinguishing value is the combination of operators with clear information about what is observed, predicted, historical or unavailable. Bus arrivals and accessibility add sources and important data contracts. Journey planning and historical analytics are separate strategic investments with ongoing operating costs.

### Verified data opportunities

- [MTA developer resources](https://www.mta.info/developers) confirms real-time and future service-alert feeds, custom extensions, frequently updated railroad schedules, and supplemented subway GTFS. The supplemented feed includes most—not all—service changes for the next seven days.
- [MTA SIRI StopMonitoring](https://bt.mta.info/developers/siri/stop-monitoring) provides stop-specific prediction queries with route/direction filters. Cache backend requests rather than issuing an upstream request for every visitor.
- [MTA accessibility guidance](https://www.mta.info/developers/display-elevators-NYCT) distinguishes fully, partially and non-accessible stations, supplies direction notes, and explains joining equipment to current outages by equipment ID.
- [Citi Bike system data](https://citibikenyc.com/system-data) provides a real-time GBFS feed and data-use terms.
- [OpenTripPlanner](https://docs.opentripplanner.org/en/latest/) supports multimodal routing from GTFS and OpenStreetMap with real-time updates. Evaluate a separate routing service rather than implementing itinerary search in the map frontend.

A shared NYC/London platform may eventually reuse feed-adapter interfaces, freshness contracts, station boards and map controls. First extract abstractions that both implementations actually need; keep agency-specific identity matching, direction inference, credentials and calendar quirks isolated. Do not make that platform refactor a prerequisite for delivering the commuter features above.
